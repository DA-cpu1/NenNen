# 桌面陪伴角色：开发规格总览

版本：0.2 草案 · 编写日期：2026-10-14 · 最近更新：2026-10-15（香港时间）

状态：供讨论和开发使用的首份完整规格。尚未开始开发，尚未完成模型试聊、Windows 打包和性能验证。文中的“必须”是验收要求，不代表功能已经实现。

## 先看这一页

我们要做一个 Windows 桌面陪伴软件：桌面上是一张可拖动、缩放的 Q 版角色；点开后有完整立绘和文字聊天。她按人设表达，能够记住有依据的信息、接受纠正，并在用户允许时主动说话。

**第一版减少角色数量和额外能力，不削减人设回复、记忆、纠正、主动陪伴和数据保存。** 三个开发阶段组成完整第一版，第四阶段用于日用完善和公开发布。

## 四阶段交付

| 阶段 | 得到什么 | 进入下一阶段的条件 |
|---|---|---|
| 一：技术与角色验证 | 可打包的最小程序、真实角色聊天、模型比较记录 | 关键技术可运行，角色试聊达到门槛 |
| 二：桌面与记忆闭环 | 桌宠、完整聊天、来源可查的记忆、纠正删除 | 重启后能接着聊，记忆相关检查通过 |
| 三：完整第一版 | 主动气泡、设置、安装与升级、连续日用 | 首版全部必需需求通过验收 |
| 四：日用完善和公开发布 | 多角色界面、教程、更长对话、发布支持 | 按新增需求验收，不降低原有标准 |

当前规划：前三阶段约 21～32 个有效开发日，日历预留约 5～8 周。是假设单人持续投入、已有静态素材的估算，不是承诺。技术验证失败或角色质量未达标时重新估算，不悄悄砍核心功能。第四阶段另估 20～35 个有效开发日，应用感知、语音、云同步不默认计入。

## 几个词的中文解释

- **SDD：**先写清需求、行为和验收方式，再据此实现；变更时同步修改相关文档。
- **Agent：**能结合人设和记忆回答，并在需要时调用我们提供的功能的程序。
- **工具：**Agent 可请求使用的功能，例如查记忆、保存称呼；不是让模型随便操作电脑。
- **接口：**两部分之间事先约定的输入和输出，使修改一部分时不必连带改全部。
- **数据库迁移：**新版软件为旧数据库增加或调整结构，同时保留已有数据。
- **token：**模型处理文字的计量单位，与中文字数不是一一对应；用于记录成本。

## 怎样使用这套文档

1. 先审阅 01、02：确认产品行为符合预期。
2. 开发前做 06 中的 T01～T03，形成真实验证记录，再固定软件库版本。
3. 按任务编号实现；一个任务只有证据齐全才能标为完成。
4. 用 07 的需求对应表检查遗漏。人设质量由试聊评价，数据行为由自动检查和真实安装检查共同验证。
5. 范围变化记录到 08，同时更新需求、设计、任务、验收。

本次只编写规格和结构样稿，没有初始化应用、安装软件库、复制角色图片或向模型发送私人聊天。数据库样稿不等于已实现的记忆系统。

开发者可使用 [validate-spec.mjs](validate-spec.mjs) 重新检查本地链接、需求对应和数据库约束。需支持 `node:sqlite` 的 Node 环境；它不是产品启动脚本。
