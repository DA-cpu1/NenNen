# 04 · Agent 工具与运行流程

## 1. 每次聊天的过程

```mermaid
sequenceDiagram
    participant U as 用户
    participant I as 聊天窗口
    participant S as 本地服务
    participant D as 数据库
    participant A as Agent与模型
    U->>I: 发送消息
    I->>S: 消息与唯一请求编号
    S->>D: 保存用户消息，读取角色版本
    S->>D: 读取未排除的近期对话与相关记忆
    S->>A: 当前消息、人设、背景、可用工具
    alt 普通聊天
        A-->>I: 经本地服务逐步显示回复
    else 需要工具
        A->>S: 工具名称与参数
        S->>S: 检查来源、归属、次数与操作编号
        S->>D: 执行并保存结果
        S-->>A: 成功或明确失败
        A-->>I: 基于真实结果生成角色回复
    end
    S->>D: 保存回复状态与模型用量
    S->>S: 满足条件时安排记忆整理
```

界面实际只与本地服务通信，图中回复箭头表示最终显示路径。正式聊天可由模型自主决定保存，沿用现有显示保护：等生成步骤结束，丢弃进入工具调用前的角色旁白，再显示最终文字。即使最后没有调用工具，也可能等整段生成完才显示；试聊无正式工具，继续逐段显示。此取舍按用户批准的最小修改执行，不增加一轮强制模型判断（08 C15）。

打开角色聊天时，服务解析并复用该角色唯一的正式会话（`mode='normal'`），再次打开不新建；首次初始化角色时同时建立人设、正式会话与设置。首版没有新建或清空聊天入口。切换到其他角色的入口时加载其独立历史和私有记忆，仅明确共享的资料可跨角色使用；试聊使用单独的 `preview` 会话。

## 2. 一次回复的输入

按顺序放入：共同事实规则 → 角色核心设定和版本 → 少量相关示例 → 用户明确共享资料 → 相关记忆 → 未排除的近期对话 → 当前消息或事件。

按用户2026-11-03要求，正式聊天、草稿试聊和固定连通检查取消应用的12,000 token输入额度及1,000 token输出上限；请求不发送应用指定的最大输出参数，由供应商自身规则决定输出。输入只受已核对的模型窗口减回复预留约束；当前模型取1,000,000窗口，按官方128K最大输出预留131,072，输入估算可用868,928。预留只是给回复留下空间，不是发送给供应商的新输出上限。本次不决定09 H2每日费用方案；独立T03评测按各批次授权参数运行，既有评测记录不追改。依据见08 C12。优先保留核心人设和当前消息，然后相关记忆、近期对话；必要时减少较早对话和示例。核心设定本身过长时在编辑页提示缩短，不静默截掉核心性格。用户单条输入首版限制 8,000 字符，超限提示分段。

上述排列是提示内容的组织顺序，不是超预算时的保留优先级。8,000 字符不等于 8,000 token，也不保证一定放得进实际模型窗口；每次调用（含工具续轮）都检查总输入与输出预留。删减可选内容后核心人设与当前消息仍放不下时，提示缩短输入/设定，不静默丢掉当前消息。完整历史仍可在本地查看，但只选预算内内容发给模型；摘要仍在第四阶段。

单条字符数按 Unicode 码点计算（普通中文与单个 emoji 各算一个，组合 emoji 可能包含多个），包括原文首尾空白；超过 8,000 时在写入前拒绝，不能截短后存入。该限制由后台执行，不只依赖输入框。

没有模型专用分词计数器时，输入按完整 JSON 的 UTF-8 字节数加 256 的协议预留保守估算，明确标为估算，不能作为供应商精确用量；该口径可能提前拒绝可装下的文字。模型实际窗口须由适配层核对后传入，不猜默认容量。准备阶段先放共同规则、完整人设（含关系、称呼、版本）与当前消息，再选正式聊天的当前称呼偏好、相关共享和私有记忆。接着由近到远加入整组历史，最后按原顺序加入示例；原话、依赖回复及引用它们的主动消息同组取舍，最终仍按消息顺序发送。不改 SQLite 原文，不生成摘要。实际调用前还必须对含工具说明、返回结果等新增内容的完整输入复查，优先移除示例和旧历史，最后才移除记忆资料。

上文的 131,072 是智谱预设的回复预留。DeepSeek Flash 预设按官方 1M 窗口保守填入 1,000,000，按关闭思考且省略输出上限时的默认值预留 8,192。应用用预留来计算能放多少历史，正式请求继续由供应商决定实际输出长度（08 C17）。[DeepSeek 模型规格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/) · [默认输出规则](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)

记忆、工具返回、聊天原文是资料，不允许覆盖产品规则。已取消/失败的角色片段不作为可靠经历。服务层根据会话 `mode` 拒绝试聊写入正式长期记忆，包括立即记忆工具；不能只依赖提示词约束。

本轮人设和可用消息从 SQLite 一起读出为独立资料，回合中途不重读“当前人设”，下一轮才跟随保存或回退后的版本。当前用户消息单独保留，历史边界固定在它之前；同一用户消息有多份回复时，先选边界内最新的一份，再检查是否完整、未被排除。最新回复不可用时不退回旧版；被排除的用户原话及依赖它的回复也不进入上下文。供用户查看的历史仍可保留这些原文，不能直接用展示接口的结果当模型输入。

默认每轮最多 3 次模型生成、4 次工具执行、总用时 90 秒；开始等待首段文字超过 30 秒显示等待状态，超时结束。额度、时限在程序控制，不能由模型自行延长。

## 3. 应用与 Agent 之间的约定

下面是我们自己的接口草图，不是 eve 或 AI SDK 已存在的方法名。实现时按所安装版本的官方文档适配。

```ts
type TurnInput = {
  requestId: string;        // 重试沿用同一个编号
  conversationId: string;  // 后端据此解析角色，不能信任模型自选角色
  userMessageId: string;
};

type TurnEvent =
  | { type: 'text'; delta: string }
  | { type: 'tool-status'; label: string }
  | { type: 'done'; messageId: string }
  | { type: 'failed'; code: string; retryable: boolean };

interface CompanionRuntime {
  run(input: TurnInput, signal: AbortSignal): AsyncIterable<TurnEvent>;
  invalidateContext(conversationId: string): Promise<void>;
}
```

应用会话 ID 与框架会话 ID 分离。数据库 `conversations.runtime_session_id` 可更换；用户看到的聊天会话不变。

当前 eve 适配采用每个应用回合新建框架会话：先由 SQLite 准备预算内输入，再用无消息 `sessions.create({ signal })` 建立空会话，保存新框架 ID，之后才允许发送。无消息创建不触发模型；映射无法落库、创建期间取消或会话内容版本改变时，拒绝继续并尝试回收空会话。旧框架 ID、运行文件或框架历史不作为续聊来源。发送入口再次复查取消、内容版本与框架映射；同一准备结果只发送一次，受理结果不明时不自动重发。受理返回事件流句柄，不代表回复成功。此处的“回合”是一次用户消息及回复，不会新增用户可见的应用会话。具体依据见 08 C05。

后台通过带版本号的内部 JSON 信封交付预算内消息；界面没有自选系统提示或窗口容量的入口。模型调用前的 AI SDK middleware 将信封还原为各自的 system/user/assistant 身份，丢弃信封之前的框架提示与历史，只保留信封之后本回合新增的 assistant/tool 续轮；出现额外用户或系统消息则拒绝。实际请求含工具说明等全部参数重新检查预算；产品不设置应用输出上限，显式有限额的固定测试仍可指定。若框架消息格式或工具资料令输入膨胀，按后台提供的位置先移除示例、再移除由旧到新的历史整组，直到放下或仅剩必需内容仍超限；不能移除共同规则、人设、当前消息或本轮工具续接。准备阶段的消息编号是候选，不代表补裁后的最终来源。缺少有效信封时只兼容 T01 固定连通探针，其余输入（含框架自动摘要请求）拒绝。适配器接入与完整 eve 流程验证按 T06 分步记录，不能将单独参数检查当成正式聊天已接通。助手回复的思考内容随消息保存在 SQLite，下一轮重建信封时一并还原为 reasoning 片段；带工具的思考模式据此原样回传 `reasoning_content`，旧消息没有这段内容时按普通文字历史处理（05 §2、08 C18）。

## 4. Agent 可以使用的工具

后台自动补入的相关记忆可以满足多数聊天；`search_memories` 用于用户追问旧事或当前背景不足时。工具只返回有限结果，不直接暴露数据库。

eve 工具只向本机业务后台交付当前框架会话编号和已检查的参数。后台用当前 eve 令牌核对请求，再确认是活跃正式回合、内容版本仍有效、时间和工具额度尚可用，最后才按会话确定角色范围。试聊不提供正式工具，后台也独立拒绝试聊访问。

| 名称 | 何时使用 | 模型提供的输入 | 返回内容 |
|---|---|---|---|
| `search_memories` | 需要找旧信息 | `query`、可选 `limit`（最多 8） | 记忆 ID、内容、来源属性、时间、修订号 |
| `remember_explicit` | 当前用户表达了有依据、未来有用的事实 | `propose` 带正文、类别、原话编号及可选属性键；`reuse` 带确认编号和旧记忆编号；`add` 只带确认编号 | `needs_review` 带候选、确认编号和原话时间，或 `saved/already_saved` 带记忆编号及修订号 |
| `correct_memory` | 用户明确纠正 | `memoryId`、`expectedRevision`、`content`、`sourceMessageId` | 新记忆 ID 或冲突说明 |
| `forget_memory` | 用户明确要求忘记 | `memoryId`、`expectedRevision`、`requestMessageId` | 忘记完成或需要明确对象 |

角色范围、共享范围、操作编号由后端注入，模型不能指定任意角色或任意用户。首版全局共享只由设置页切换或明确的共享操作处理，普通记忆工具默认当前角色。

每个工具统一返回：

```json
{
  "ok": false,
  "code": "STALE_REVISION",
  "message": "这条记忆刚被更新，请读取新版本后再处理",
  "retryable": true
}
```

其他错误码：`INVALID_INPUT` 参数不合法、`SOURCE_NOT_ALLOWED` 来源不属于当前可用消息、`NOT_FOUND` 无可访问对象、`AMBIGUOUS` 指代不清、`BUDGET_EXCEEDED` 超预算、`STORAGE_UNAVAILABLE` 无法落盘、`CANCELLED` 已取消。

输入检查能验证消息归属、版本和字段，不能完全证明“用户是否真的表达了这个意思”。是否值得保存由模型理解，靠共同事实规则、工具说明、来源审计、用户纠正和验收降低误判。引用、假设、第三方事实、角色编造、凭据和验证码不能保存成用户事实；一次性要求不能变成长期互动要求。不确定就跳过，后台候选流程继续补漏。

已登记工具访问的正式回合提供 `remember_explicit`，并标明本轮唯一允许使用的来源编号，不检查保存关键词。明确纠正或忘记的回合仍只开放对应修改工具及检索，不混用新增保存；原有修改意图判断保留。试聊不提供正式工具，后台独立核对正式模式、当前来源、取消、版本和额度。工具成功回执仍是报告保存成功的依据。

收到提议时，先按同一来源、同一属性键、提议正文关键词的顺序查有效私有记忆，最多给出五条。没有候选可以写入，长期同文直接复用。需要比较时在本轮内存登记原提议和候选版本，等模型用确认编号选择复用或新增。确认时在写入事务中复核来源和旧条，确认新增还要复查候选和角色记忆版本。确认编号随回合结束清掉。提议与确认各占一次工具额度，模型仍受三次生成限制（08 C20）。

## 5. 只有程序可调用的功能

| 功能 | 职责 |
|---|---|
| `build_context` | 预算内准备人设、最近对话、相关记忆；过滤被忘记来源 |
| `extract_candidates` | 用新增对话提取候选项，返回规定格式 |
| `commit_candidates` | 在事务内检查冲突与版本并写入 |
| `publish_bubble` | 发送前检查开口条件，写入发送记录并显示 |
| `rebuild_runtime_context` | 纠正/忘记后淘汰旧缓存，用干净上下文新建运行会话 |
| `migrate_database` | 软件升级时备份并升级结构 |

不提供任意 SQL、Shell、随意读写文件、自改人设工具。程序计时，模型不负责“持续盯着时间”。

## 6. 自动整理的全过程

```mermaid
flowchart TD
    A[新增聊天已保存] --> B{达到批量或空闲条件?}
    B -->|否| Z[等待新消息或空闲事件]
    B -->|是| C[仅正式会话：固定来源范围与三个版本]
    C --> D[登记整理任务及唯一批次编号]
    D --> E{调用前：正式会话、来源和版本仍有效?}
    E -->|否| K[跳过旧任务，确有需要才重排]
    E -->|是| L[读取未排除的新原文及相关旧记忆]
    L --> F[模型输出零到多条候选记忆]
    F --> G{格式、来源、范围和版本通过?}
    G -->|否| H[丢弃过时结果或记录失败、按规则重试]
    G -->|是| I[事务内新增、替代、复用或跳过]
    I --> J[任务完成，推进已处理位置]
```

候选格式示例：

```json
{
  "candidates": [{
    "action": "add",
    "kind": "preference",
    "memoryKey": "preferred_name",
    "content": "用户希望被称为阿达",
    "sourceMessageIds": ["msg-user-001"],
    "expiresAt": null,
    "replacesMemoryId": null
  }]
}
```

允许 `add / replace / reuse / skip`。整理优先把已关联本批原话的有效私有记忆交给模型，再用关键词补足。模型确认同义时用 `reuse`，提供 `memoryId` 和 `sourceMessageIds`。程序核对来源在本批内，并核对旧记忆归属、有效期与实际展示的修订号，只登记来源。`replace` 核对旧值后替换。该流程无删除或修改人设动作。经历要有实际对话支持，角色编造的细节不能作为依据。

服务层在登记任务、调用模型前和提交候选时检查 `mode='normal'`；`preview` 不进入正式整理，即使直接调用内部接口或恢复旧任务也须拒绝。任务记录角色记忆版本、共享记忆版本及该会话 `context_epoch`，读取来源时排除已忘记消息。

业务后台在启动、正式原话保存、正式回复结束与模型配置生效后检查整理。空闲、额度顺延和退避由下一次到期时间唤醒。一次只执行一项整理，使用 AI SDK 发起单次请求，领取时开始计 90 秒。退出或更换密钥时取消当前整理，退出须等 SQLite 收尾；异常退出留下的运行由下次启动在租约到期后复核并恢复。

用户纠正、忘记或删除来源后，只处理依赖变化内容的范围：①尚未开始的受影响任务标为 `stale` 并跳过，真正调用模型前再核对版本；②运行中的受影响任务尝试取消；③提交事务仍核对三个版本和来源权限，任何旧结果都不得写入或推进已处理位置。检查后到模型调用之间发生变化也由取消和提交检查兜底；已发生用量不保证因取消退回。

只有剩余可用来源确实仍需整理时，才基于新状态登记新批次；不无条件重做所有角色的任务。角色私有变更限制在相关角色/会话，共享变更影响实际依赖共享资料的运行；关联无法细分时作废该依赖范围内的上下文，不能沿用可疑旧内容。具体版本用途见 05 §4。

同一批次完成标记、写入、处理位置一起提交。即使已获得模型回复后程序崩溃，也只会重新请求或重用已落库结果，不产生两份记忆。

## 7. 忘记的全过程

1. 确认目标记忆可访问，且当前用户确实提出忘记请求；指代不清则问具体对象。
2. 停止受影响的旧回复并尝试取消模型调用，已显示部分标为“未完成”，拒绝其后续片段和完成事件；提升相关角色/共享记忆版本及受影响会话的内容版本，使旧整理和回复失效。
3. 同一事务里清空目标及同一属性链相关历史正文，清理来源片段、关键词/未来向量索引，登记来源消息排除范围。
4. 按 §6 跳过受影响的待执行整理、尝试取消正在运行的整理，并保持提交版本检查；其他依赖被排除来源的记忆也失效或从剩余独立来源重建。第四阶段有摘要后，同步标为失效，首版不新增摘要生成。
5. 废弃旧框架会话，清理应用可控制的运行缓存和调试落盘副本，用经过过滤的历史重新建立上下文。
6. 确认新上下文无该信息后，才告知“已忘记”，随后才能基于干净上下文继续回复。若缓存清理失败，显示处理中/失败，不报告成功。受影响的当前回复由服务带记忆变更原因结束，聊天提示旧回复已停止。若忘记来自当前回复中的工具调用，该旧运行同样失效，成功提示由服务确认或由重建后的运行生成。

首版对多事实同条消息采用整条排除，不承诺精准删除句中一个词。之前已经发送给模型服务的内容无法通过本地删除撤回；设置说明服务商数据处理范围。手动导出的旧备份也不会被静默改写。

## 8. 主动互动流程

```mermaid
flowchart TD
    A[到达下一次检查时间] --> B{开启、未免打扰、未锁屏、未聊天?}
    B -->|否| X[跳过并计算下次时间]
    B -->|是| C{评估次数和费用预算允许?}
    C -->|否| X
    C -->|是| D[读取人设、时间、最近主动消息]
    D --> E[模型选择安静或生成短句]
    E --> F{选择开口且发送条件仍满足?}
    F -->|否| X
    F -->|是| G[用机会编号登记、显示、不抢焦点]
    G --> H[记下已发送与下次时间]
```

气泡交付由唯一机会 ID 去重。首版优先避免重复打扰：先登记已安排，再通知窗口；崩溃可能丢一条气泡，不自动重播。文档不承诺跨进程崩溃下视觉显示“恰好一次”。

每次机会固定发出消息的角色 ID；`publish_bubble` 由服务定位该角色的正式会话，将 `role='proactive'` 消息和发送记录关联保存，并核对二者的角色一致。不取当前打开窗口的会话 ID，不写入其他角色或 `preview` 会话。没有有效正式会话时跳过并记录原因，不临时创建试聊或跨角色代发。

## 9. 取消、断网、退出

- 点击停止：取消正在等待的模型和流式显示；尚未开始的工具不再执行。
- 已经提交的数据修改不能假装被撤销。界面保留“称呼已保存”等实际操作状态，重试不会再写一次。
- 网络重试只针对可安全重试步骤；工具写入通过操作编号去重，不能把整轮无条件重放。
- 数据库不可写时，保留本轮可见文本并明确“未保存”；恢复后按原请求编号重试保存。
- 回复终态与运行用量在一个短事务中一起保存，任一失败全部回滚。进程仍在时暂存本轮待写结果，同编号同正文重试只补写原结果，不再次请求模型；补写仍失败时继续保留可见文字。若应用已经退出，内存中未写成的文字无法保证找回，启动恢复把遗留进行中记录标为失败，不冒充完成。
- 退出时取消请求并保存已提交状态；再次启动把过期运行租约恢复到可重试，主动问候不补发。
- 改模型或人设不会重写旧消息；新运行记录实际使用的版本和模型，便于定位质量变化。
