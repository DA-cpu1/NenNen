# 概念手册

背景概念的完整解释与复习材料。**大白话写就、术语锚点齐全、场景全部来自本项目**——专业版解释互联网上到处都有（MDN、官方文档），这里只记别处搜不到的：按你的水平校准的解释 + 本项目的真实场景。

- 代码注释负责「读到那行代码时当场看懂」（就地一两句）
- 本手册负责「系统复习、日后查阅」——两边同源，深度不同
- 找法：全局搜术语名（Ctrl+Shift+F），手册条目和用到它的代码一起跳出来
- 条目只记「角色」（哪一层的事），不记文件行号——代码会重构，角色不会变

维护规则见 AGENTS.md；新概念首次出现时由写代码的会话顺手沉淀，漏了也无害（发现即补）。

## 一、网络与安全

### 会话暗号（session token）

**是什么**：程序自己随机编的一句口令，用来核对「来电的是不是自己人」。注意：是我们**自己编给自己用**的——两个进程都归本程序管；网页登录时那种 token 是服务器下发给你的，是另一回事。

**为什么需要它**：后台服务只接本机（127.0.0.1）的电话，但你电脑上**任何进程**都能往本机端口打电话。不设口令，一个来路不明的脚本就能打进后台偷读聊天记录。

**在本项目里的角色**：desktop 层每次开机用 32 字节纯随机数现编一句 → stdin 管道送后台 → 此后每个 HTTP 请求头 `x-session-token` 都要带、后台逐个核对 → 每次开机换新，泄露了重启即作废。

**相关概念**：[[管道（stdin/stdout）]]、[[HTTP 无状态]]、[[HTTP 请求头]]、[[随机数与 base64]]

### HTTP 请求头（request header）

**是什么**：HTTP 请求开头部分的「名字： 值」清单。HTTP 协议只规定了格式（一堆 `名字: 值`），往里放什么靠双方约定——它只是搬运工，不理解内容含义。名字以 `x-` 开头是「自定义头」的惯用前缀。

**为什么需要它**：这是往每个请求里附带信息（身份、格式偏好）的标准位置。类似的常见头：`Authorization: Bearer xxx`（调各家 API 的标准姿势，我们的智谱密钥就这么发）、`Cookie`（浏览器登录态）。

**在本项目里的角色**：service/server.ts 核对 `x-session-token` 头；`content-type: application/json` 声明回话格式。**不放 URL 里**——URL 会被各种日志原样记下来，请求头不会。

**相关概念**：[[HTTP 无状态]]、[[会话暗号]]、[[状态码]]

### HTTP 无状态（stateless）

**是什么**：HTTP 协议天生没有记忆——服务器处理完一通请求就忘了你是谁，不存在「开头自我介绍一次、后面就认识你」。每个请求都是独立陌生人。

**为什么需要它**：这直接决定了安全设计——既然后台不记得谁打过电话，**每个请求都必须自带身份证明**（暗号装在请求头里跟着走）。也解释了为什么身份核对每个请求都跑一遍，而不是启动时验一次就完。

**在本项目里的角色**：service 层每通电话核对暗号的根本原因。以后学 Cookie/JWT 会发现它们也是在补「无状态」这个缺口。

**相关概念**：[[HTTP 请求头]]、[[会话暗号]]

### 状态码（status code）

**是什么**：每个 HTTP 回话开头的三位数字，一眼表明「这通电话的结果」。记住常用的就够：

| 码 | 含义 | 本项目场景 |
|---|---|---|
| 200 | 成功 | 带暗号打 /health |
| 401 | 没对上身份（未认证） | 不带/带错暗号 |
| 404 | 没这个东西 | 路径写错 |
| 500 | 服务器自己出意外 | 内部兜底 |
| 502 | 上游（我依赖的人）出问题 | 模型调用失败 |
| 503 | 现在没法服务 | 没配密钥就打 /model/ping |

**为什么需要它**：让调用方不用解析内容、看第一个数字就知道下一步该重试、报错还是放弃（4xx 是你的问题，5xx 是我的问题）。

**在本项目里的角色**：desktop 层启动自测就是核对两通电话的状态码（200 和 401）。

**相关概念**：[[HTTP 请求头]]

### 回环地址与端口（127.0.0.1 / port）

**是什么**：回环地址 127.0.0.1 是「本机自己」的地址——发往它的网络包出不了这台电脑，外面的网络也进不来，等于一根只有本机能拨的电话线。端口是电话线上的分机号（0～65535），一台机器上每个监听中的程序占一个号。

**为什么需要它**：后台服务必须「界面够得着、外人够不着」——绑 127.0.0.1 就是这个边界。端口写死会撞号（被别的软件占了就起不来），所以传 0 让系统现场挑个空闲的。

**在本项目里的角色**：service 层总机 `listen(0, '127.0.0.1')`；实际分到的号码通过 READY 行报给主进程。

**相关概念**：[[会话暗号]]（回环挡外人，暗号挡本机里的外人）

### 随机数与 base64（randomBytes / base64url）

**是什么**：`randomBytes(32)` 生成 32 字节**密码学随机数**——和掷骰子那种「伪随机」不同，它由操作系统保证不可预测，32 字节的组合数约 10^77，逐个试到宇宙热寂也试不完。base64url 是把随机字节编码成「可见字符」（字母数字）的方式，方便当字符串传递，不是加密、不增加安全性。

**为什么需要它**：暗号必须「猜不出」才配当暗号。每次开机重新生成，泄露了重启即作废。

**在本项目里的角色**：desktop 层生成暗号：`randomBytes(32).toString('base64url')`。

**相关概念**：[[会话暗号]]、[[sha256 指纹]]

## 二、操作系统与进程

### 进程与 spawn（process）

**是什么**：进程 = 一个正在运行的程序实例，有自己独立的内存空间——A 进程崩溃不会连累 B 进程。`spawn` = 从当前程序里启动另一个全新进程（指定用什么程序跑什么文件）。

**为什么需要它**：重活（调模型、写数据库）单独放一个进程，卡死或崩溃都不会把界面拖下水；这也是规格把界面和后台劈开的物理基础。

**在本项目里的角色**：desktop 层启动业务后台，业务后台再启动 eve 独立服务，形成 Electron → 业务后台 → eve 三层。退出要检查两个 Node 进程均已回收；eve 还检查父进程是否存在，防业务后台被强制结束后留下孙进程。

**相关概念**：[[管道（stdin/stdout）]]、[[回调（callback）]]

### 管道（stdin / stdout）

**是什么**：操作系统在一对父子进程之间接的数据通道。父进程写子进程的 stdin，子进程从自己那头读到；子进程写 stdout，父进程收到。管道内容不会自动出现在启动参数或文件里；程序若主动打印、保存，仍会泄露，同一进程里的依赖也能接触内存数据。

**为什么需要它**：不把机密放在命令行参数和环境变量这两条常见的暴露路径上。管道是本项目选定的交付方式，使用后仍需避免日志、错误对象和工作流记录保存机密，不是“任何人都截不到”的保证。

**在本项目里的角色**：有两跳：desktop → service 的第 1 行是业务令牌、第 2 行是模型密钥；service → eve 的第 1 行是模型密钥、第 2 行是 eve 路由令牌。发送端明确写换行，接收端收齐两行才使用，不能依赖密钥文件自带换行。

**相关概念**：[[进程与 spawn]]、[[流（stream）]]、[[会话暗号]]

### 流（stream）

**是什么**：一种「数据分批送达」的传送方式，像水龙头滴水——不是一次性给你一整桶，而是一滴一滴来。读的人不能假设「一次收到的就是完整数据」，要先攒进缓冲区（buffer），见到约定的结束标记（比如换行符）才算一份凑齐。

**为什么需要它**：系统不保证一次送多少。假设「一次事件 = 一行」的程序会时灵时不灵——最恶心的一类 bug。管道是流，HTTP 响应体也是流。

**在本项目里的角色**：desktop 层收 READY 行、service 层收暗号，都是「攒 buffer、等 `\n`」的写法。

**相关概念**：[[管道（stdin/stdout）]]、[[回调（callback）]]

### 环境变量（environment variable）

**是什么**：操作系统给每个进程配的一张「便签清单」，进程里跑的**任何代码**（包括第三方依赖包）都能整张读到。常用来传不重要的配置，比如告诉服务器「监听几号端口」。

**为什么需要它**：端口、运行目录等配置不必写死在源码里。环境变量可被当前进程的依赖代码读取，也可能随子进程继承或被诊断工具收集，所以本项目只用它传公开配置，禁止密钥和令牌走这条路（03 §3）。

**在本项目里的角色**：两类用途分得清清楚楚：端口号、HOST 这类公开配置可以用（如 eve 服务器认 `PORT`）；暗号与模型密钥永远不用，只走[[管道（stdin/stdout）]]。

**相关概念**：[[管道（stdin/stdout）]]、[[进程与 spawn]]

---

### 命令行参数（command-line argument / argv）

**是什么**：启动程序时跟在程序名后面、用空格隔开的一串文字，比如 `node service.js --db C:\data\companion.db`。程序内部用 `process.argv` 数组读到它们：第 0 位是程序自己、第 1 位是脚本名，之后才是参数，所以代码里常用 `process.argv.slice(2)` 取真正的参数。

**为什么需要它**：和[[环境变量]]一样，是把「配置」从代码里拿出来的通道；它比环境变量更显眼——启动命令写在一起，一眼看全。代价相同：能看清进程启动命令的本机程序都读得到，所以只放非机密。

**在本项目里的角色**：主进程启动业务后台时用 `--db 路径` 告诉它数据库文件在哪。路径不是机密（拿到路径读不走密钥），可以走这条通道；暗号与密钥仍只走[[管道（stdin/stdout）]]。

**相关概念**：[[环境变量]]、[[进程与 spawn]]、[[用户数据目录（userData / AppData）]]

---

### 用户数据目录（userData / AppData）

**是什么**：操作系统给每个用户账户划出的「放个人应用数据」的标准位置，Windows 上通常在 `C:\Users\用户名\AppData\Roaming\` 下。Electron 的 `app.getPath('userData')` 直接返回本应用在该位置的专属子目录。

**为什么需要它**：程序安装目录（如 Program Files）普通用户没有写权限，数据库放那里一写就失败；而且卸载重装程序时个人数据应该留下来，不能跟着程序一起被删。每个系统的标准位置不同，用系统 API 取（而不是把路径写死）才能在换机器、换用户名时仍然正确。

**在本项目里的角色**：数据库文件 `companion.db` 的家（05 §1）。主进程取到路径、确保目录存在，再通过 `--db` 参数交给业务后台打开。

**相关概念**：[[命令行参数]]

---

### 逻辑像素与显示缩放（DIP / scale factor）

**是什么**：DIP（device-independent pixel，设备无关像素）是「不管屏幕多细腻，都按同一把尺子量」的长度单位。Windows 的显示缩放（如 150%）= 一个 DIP 对应 1.5 个物理像素：程序里量出 100 的长度，高分屏上实际点亮 150 个物理像素。

**为什么需要它**：同一个界面要在 100% 和 150% 缩放的屏幕上都摆得下，就必须有统一单位；直接拿物理像素当坐标，换个缩放设置就全错位。Windows 还允许多台显示器各自不同缩放，跨屏移动窗口时换算更绕。

**在本项目里的角色**：Electron 的窗口位置、尺寸、光标坐标统一用 DIP（getBounds / getCursorScreenPoint），桌宠拖动与位置保存因此不碰物理像素；多屏不同缩放时，恢复位置的「放回可见区」按各屏工作区的 DIP 矩形计算。

**相关概念**：[[透明窗口与无边框窗口（transparent / frameless）]]、[[用户数据目录（userData / AppData）]]

## 三、数据库

### 事务（transaction）

**是什么**：把若干步数据库操作打包成「要么全做成、要么全部当作没发生」的原子单位。中途任何一步失败，已做的自动撤销（回滚）。

**为什么需要它**：防「撕裂」。项目里的真实例子：迁移 = 施工（建表）+ 记账（登记版本号）两步。不绑进事务的话——表建了账没记，下次启动重做、撞上已存在的表，程序起不来；账记了表没建，程序以为自己是最新，用的时候才炸。绑进事务后这两种状态物理上不可能出现。

**在本项目里的角色**：data 层每个迁移都包在 `sqlite.transaction(...)` 里；规格 05 里所有「同一事务」的字眼（忘记流程、记忆提交）都是这个机制。

**相关概念**：[[迁移（migration）]]、[[WAL 预写日志]]、[[外键]]

### 原子自增（SQL 自增表达式）

**是什么**：让数据库在**一条指令**里完成「取出当前值、加一、写回」的写法：`.set({ count: sql`count + 1` })`。原子 = 不可分割：数据库保证这个过程要么完整做完、要么完全没做，别的写入插不进中间。

**为什么需要它**：若拆成三步「SELECT 读出 5 → 程序里算 6 → UPDATE 写 6」，读和写之间别的写入可能已把它改成 7，你的 6 会把 7 盖掉（丢失更新）。单个后台进程眼下碰不到，但按「会被并发调用」的写法写，后面加功能才不会埋雷。

**在本项目里的角色**：`/db/ping` 的 POST 用它给 `app_state.globalMemoryEpoch`（共享记忆版本号）+1，是 T01 数据库贯通的那「一次真实业务写」。

**相关概念**：[[事务]]（事务把多条语句打包成原子；自增表达式是单条语句内部的原子）

### 撞键即更新（ON CONFLICT / upsert）

**是什么**：一条 SQL 同时表达「没有就插入、有就更新」的写法：先正常 INSERT，撞上主键或唯一约束时按事先写好的分支改成 UPDATE。数据库在一步内做完判断和写入。

**为什么需要它**：「先 SELECT 查有没有、再决定 INSERT 还是 UPDATE」的两步写法中间有条缝——两次并发写同一个键，可能都查到「没有」，然后各插一行（或后插的撞主键失败）。把判断交给数据库，缝就不存在了。

**在本项目里的角色**：窗口位置这类设置存在 app_settings 表（键为主键），每次拖动/缩放结束都会用同一个键保存。writeSetting 用 ON CONFLICT 保证反复保存是覆盖同一条，而不是越存越多。

**相关概念**：[[原子自增（SQL 自增表达式）]]、[[事务（transaction）]]

### WAL 预写日志（Write-Ahead Log）

**是什么**：SQLite 的一种日志模式。不开它（默认「回滚日志」模式）：写数据的瞬间会锁住，读的人被挡住。开了它：改动先记到旁边的小本子文件（`.db-wal`）里，读的人永远看完整稳定的主文件，空闲时再把小本子正式誊进主文件——读写互不阻塞。

**为什么需要它**：本项目的常态就是「界面一直读 + 后台一直写」。不开 WAL，后台每写一批记忆，正在滑动的聊天窗口就卡一下。

**在本项目里的角色**：data 层唯一连接入口统一开启（`pragma('journal_mode = WAL')`），不存在漏开的连接。

**相关概念**：[[事务]]（两者常配合：WAL 管读写并行，事务管原子性）

### 外键（foreign key）

**是什么**：一张表里「指向另一张表某行」的字段，比如「记忆 #7 的依据是消息 #52」。开了外键检查后，数据库变成门卫：任何会造成「指向空号」的操作（删掉消息 #52 却留下指向它的记录），当场拒绝执行。

**为什么需要它**：防悬空引用。不开的话数据不会立刻出错——而是几个月后程序读到「指向不存在的消息」的记录，要么崩溃要么悄悄算错，烂在最难排查的地方。SQLite 为兼容老项目默认关着它，且**每个连接各自开关**，所以必须在唯一入口强制打开。

**在本项目里的角色**：data 层连接入口统一开启；「忘记」流程（规格 05 §6）依赖这类完整性约束兜底。

**相关概念**：[[事务]]、[[迁移（migration）]]

### 迁移（migration）

**是什么**：带编号的「数据库装修单」+ 库里的「装修记录本」（schema_migrations 表）。程序启动翻记录本：做过的核对指纹，没做的补做。解决「老用户的库还是旧结构、新版程序要新结构、又不能删库重来」的升级问题。

**为什么需要它**：`CREATE TABLE IF NOT EXISTS` 对已存在的旧表什么都不做——新加的列、改的约束统统不生效，等于没升级。升级机制必须能表达「改」，不止「建」。

**在本项目里的角色**：data 层的迁移清单 + 启动执行器；两条铁律靠它兜住——已发布的单子绝不修改（改了老用户对不上账）、库比程序新就拒绝写入（防回滚安装写坏新库）。

**相关概念**：[[事务]]、[[sha256 指纹]]、[[外键]]

### sha256 指纹（checksum / hash）

**是什么**：一种「内容指纹」算法——任意内容算出固定长度的字符串，同样内容永远同指纹，改一个标点指纹整个变，而且**从指纹反推不出原文**。

**为什么需要它**：发现「东西被事后改过」。迁移单记下执行时的指纹，下次启动重算对比——指纹对不上说明有人改了已发布的单子，不同用户的库就会出现「同编号不同内容」，排查时对不上账。

**在本项目里的角色**：data 层校验迁移的内容摘要（checksum 字段）；本地验收记录也用它辨认具体安装包，避免把不同构建的测试结果混在一起。文件指纹只能辨认内容，不能证明功能正确或反推源码版本。

**相关概念**：[[迁移（migration）]]、[[随机数与 base64]]

### CHECK 约束（CHECK constraint）

**是什么**：建表时写给数据库的一条「收货标准」，比如「mode 这一列只收 normal 或 preview 两个值」。之后的每次写入数据库都替你验货：写进不认识的值当场报错，而不是混进库里让代码到处判空。

**为什么需要它**：靠程序代码检查会漏——总有一条新代码忘了判、或拼错字符串。数据库层的约束是最后一道闸门，程序写漏了检查它也拦得住，错误在写入瞬间就暴露。

**在本项目里的角色**：会话表 mode（normal/preview）、消息表 role（user/assistant/proactive）、工具操作表 status（pending/committed/failed）等枚举字段全靠 CHECK 兜底（T04 结构测试验证过拦截）。

**相关概念**：[[外键]]、[[部分唯一索引]]

### 部分唯一索引

**是什么**：一条「只对部分行生效」的唯一性规则，建表时用 `CREATE UNIQUE INDEX ... WHERE 条件` 声明。比如「每个角色最多一行 is_active=1 的版本」——只盯生效行，历史版本（is_active=0）随便存多少行。

**为什么需要它**：普通唯一索引是全表一刀切。「一个键只许出现一次」会把合法的历史记录也拦下；部分唯一索引只约束「现在生效的」那一小撮行，既保住历史又不许同时冒出两个「当前」。

**在本项目里的角色**：人设版本表保证每个角色同一时刻只有一个生效版本（T04）；记忆表的「同属性最多一条 active 记录」也是这个手法（05 §5，T07 接手）。

**相关概念**：[[CHECK 约束]]、[[外键]]

### 幂等与防重（idempotent）

**是什么**：同一个操作做一次和做多次效果相同——再点一次「保存」不会存出第二份。实现思路是给每件事配一个唯一编号，数据库用唯一约束拦第二次：重试、网络重放带着同一个编号再来时，直接返回第一次的结果。

**为什么需要它**：网络世界里「请求发出去但回音丢了」是家常便饭，调用方只能重试。如果每次重试都真的再执行一遍，用户说一次「记住我叫阿达」会存出两条记忆、一句聊天会显示两遍。

**在本项目里的角色**：三层防重各有编号——消息表的 client_request_id（防同一句话重复入库）、工具操作表的 operation_key（防同一操作重复执行，T04 的 tool-ops）、主动消息的机会 ID（T10）。编号由程序拼接（会话+消息+工具+目标），不是随机数——随机数每次都不同，认不出「同一件事」。

**相关概念**：[[事务]]、[[原子自增]]、[[部分唯一索引]]

### 版本号对账（epoch）

**是什么**：给容易被并发修改的数据配一个「每次改动 +1」的计数器。后台任务开工时抄下当时的数字，落库前再核对一遍：没变说明干活期间没人动过，结果放心写入；变了说明底下的数据被改过，旧结果作废重来。

**为什么需要它**：后台整理记忆要花几十秒调模型，期间用户可能纠正或忘记某条记忆。没有对账，任务会拿着改之前的旧状态算出结果、写进改之后的新状态里——脏数据无声混入。它是「乐观并发控制」的最小实现：不锁数据赌没冲突，用版本号在提交瞬间发现冲突。

**在本项目里的角色**：三个版本号各管一段（05 §4）——app_state.global_memory_epoch（跨角色共享资料）、characters.memory_epoch（某角色私有记忆）、conversations.context_epoch（某会话可用内容）。data/epochs.ts 是唯一提升入口，SQL 原子自增且必须在同一事务里和业务变更一起提交。

**相关概念**：[[事务]]、[[原子自增]]、[[幂等与防重]]

## 四、JavaScript

### 被动事件监听（passive listener）

**是什么**：浏览器对滚动类事件（wheel、触摸滑动）的一种默认约定：监听器承诺「不调用 preventDefault 去阻止默认滚动」，浏览器就放心地一边滚动一边执行代码，不必等代码先跑完。要在监听器里拦默认行为，必须在 addEventListener 时明确写 `{ passive: false }`。

**为什么需要它**：桌宠的 Ctrl+滚轮缩放要拦下浏览器默认行为（Chromium 的「Ctrl+滚轮缩放整个页面」），自己改窗口大小。不改 passive，preventDefault 会被浏览器忽略并报错——「想拦却拦不住」的隐形坑。

**在本项目里的角色**：桌宠页给角色图的 wheel 监听以 `{ passive: false }` 注册：按住 Ctrl 时 preventDefault 挡掉页面缩放，改为通知主进程缩放窗口；不按 Ctrl 时不拦截。

**相关概念**：[[回调]]

### Promise / async / await

**是什么**：Promise = 一张「取货凭证」——函数现在还没拿到结果，但凭证保证将来要么兑到货（resolve）、要么告诉你拿不到及原因（reject）。`await` = 把凭证递过来说「货到了再走下一步」。JS 是单线程流水线，等的时候线程去干别的，不死等——这是它还能同时服务很多请求的秘密。

**为什么需要它**：启动总机（listen）要几十毫秒，但端口是系统分配的，**只有监听成功「回电」那一刻才知道是几号**——所以「发货」（resolve）必须写在那通回电里，不能紧跟在 listen 后面（那时货还没到，查端口拿到 null）。

**在本项目里的角色**：service 层 `startBackendServer()`（凭证发放端）、desktop 层 `startBackend()`（等报到）、main 里所有 `await fetch(...)`（等电话结果）。

**相关概念**：[[回调（callback）]]、[[流（stream）]]

### 回调（callback）

**是什么**：「好了叫我」的电话号码——把一个函数交给别人，让对方在事情完成时替你调用它。`await` 的底层就是它：回调是机制，Promise/await 是让回调写起来不那么绕的语法糖。

**为什么需要它**：JS 单线程不能死等，一切「需要等的事」（监听成功、数据到达、请求返回）都靠回调通知。事件监听（`on('data', ...)`）也是回调：事件每发生一次，你的函数被调一次。

**在本项目里的角色**：`server.listen(0, '127.0.0.1', 回调)`（监听成功回电）、`child.stdout.on('data', 回调)`（管道来水就调）、`process.stdin.on('end', ...)`（管子断了就调）。

**相关概念**：[[Promise / async / await]]、[[流（stream）]]

---

### 依赖注入（dependency injection / 注入函数）

**是什么**：一个模块不自己去 `import` 需要的具体实现，而是由使用者把现成的实现「递」进来；函数参数是最常见的载体。`startBackendServer(token, { db: { readEpoch, bumpEpoch } })` 里那两个函数就是被递进来的。

**为什么需要它**：模块只依赖「约定长什么样」（有这两个函数、返回数字），不依赖「具体谁来干」。测试时递假函数（固定返回值、不碰真实文件），运行时递真数据库——同一份总机代码两种场合通吃；同时逼着分层清晰：总机只管接电话对暗号，开库是后台入口的事。

**在本项目里的角色**：业务总机的模型自测、换密钥、数据库读写全是注入的：`options.pingAgent`、`options.rotateModelKey`、`options.db`。

**相关概念**：[[本地模拟与测试替身]]、[[回调]]

## 五、构建与框架

### React 组件、状态与受控表单（component / state / controlled input）

**是什么**：组件是一块界面及其交互代码；状态是 React 为这块界面保存、变化后会重新显示的值。受控表单把输入框内容放进状态中，而不是让每个输入框各自记一份。

**为什么需要它**：编辑人设时要保留未保存草稿、取消后恢复原件，也要在后台保存时禁止继续修改。所有输入用同一份草稿，才能统一处理这些动作。

**在本项目里的角色**：ui 层复制已保存设定作为草稿；输入只修改页面内存，明确保存才经固定通道写入 SQLite。关闭聊天窗口只是隐藏，草稿仍留在当前页面；切页时有未保存确认。

**相关概念**：[[回调（callback）]]、[[Promise / async / await]]、[[幂等与防重（idempotent）]]

### CSS Modules 与页面布局

**是什么**：CSS 描述界面的颜色、间距和排列。CSS Modules 给每个组件样式自动加上不同名字，避免两个文件同名样式互相覆盖。

**为什么需要它**：聊天页和设置页都可能有卡片、标题和按钮，各页的样式不能改着改着串到另一页。

**在本项目里的角色**：ui 层每个组件引用自己的 `.module.css`；颜色沿用全局变量，正文可滚动，保存按钮留在窗口底部，窗口缩窄时调整排列。

**相关概念**：[[React 组件、状态与受控表单（component / state / controlled input）]]、[[编译与构建产物（build）]]

### 模态确认框（modal dialog）

**是什么**：打开后要求先处理当前选择的对话框。原生 dialog 会把键盘焦点限制在框内，关闭后返回之前的位置。

**为什么需要它**：放弃草稿和回退版本会替换正在编辑的内容，需要给用户明确的继续、取消或确认选择，避免鼠标或键盘误操作。

**在本项目里的角色**：ui 层在离开未保存设定、取消修改、回退人设时显示确认框；Escape 代表继续编辑或取消，不会自动丢弃内容。

**相关概念**：[[React 组件、状态与受控表单（component / state / controlled input）]]

### 框架（framework）

**是什么**：一套别人写好的「半成品程序骨架」——定好了文件怎么摆、代码怎么写、流程怎么走，我们往里填自己的内容。和「库」（如 better-sqlite3，我们 import 它、它听我们的）方向相反：框架是它调用我们的代码。

**为什么需要它**：聊天有一堆通用难题（会话存档、崩溃后续聊、中途取消），自己写容易踩坑。框架把这些包掉，代价是接受它的规矩。

**在本项目里的角色**：eve 管模型与工具执行、运行会话和步骤进度；应用仍负责 SQLite 聊天、记忆、权限和重试规则。框架缓存可以重建，不能代替应用数据，也不保证中断中的请求原地恢复。

**相关概念**：[[作者目录（authored directory）]]、[[编译与构建产物（build）]]

### 编译与构建产物（build）

**是什么**：把人写的源代码「翻译」成机器能直接运行的成品文件，这一步叫编译（build），翻出来的成品叫构建产物。源代码是图纸，构建产物是照图纸造出的机器。

**为什么需要它**：成品运行快、不依赖开发工具。代价是：改了源代码必须重新编译才生效——忘记这一步就会出现「明明改了怎么没变化」的经典事故。

**在本项目里的角色**：仓库里已有两套：electron-vite 把 `src/` 编译到 `out/`（主进程+界面）；eve 把 `agent/` 编译到 `.output/`（它的服务器）。两者都是构建产物，被 .gitignore 挡在仓库外。

**相关概念**：[[框架（framework）]]、[[作者目录（authored directory）]]

### 作者目录（authored directory）

**是什么**：框架指定的一个文件夹，位置和文件名由框架定死，我们往里放「我们的配置和代码」。文件夹本身就是交给框架的合同。

**为什么需要它**：框架靠固定位置找到该读什么。放错地方的文件框架根本不看，写了等于没写——这类问题不报错、只是被静默忽略，排查起来最费时间。

**在本项目里的角色**：`app/agent/` 是 eve 的作者目录（`agent.ts` 定模型、`instructions.md` 目前放 T01 自测身份说明）。注意它和 `app/src/agent/`（我们自己的适配代码，规格 03 §4 的分层）是两回事：前者给 eve 读，后者给我们的后台服务用。`app/characters/` 是另外保存的角色内容样稿，当前尚未接入；把文字放进去不会自动改变运行中的身份。

**相关概念**：[[框架（framework）]]、[[编译与构建产物（build）]]

### 序列化与工作流检查点（serialization / checkpoint）

**是什么**：序列化是把内存里的值改成可保存、可传输的形式，例如把对象变成 JSON 文字；反序列化是读回来。检查点是长流程中保存的一份“执行到了哪里”的记录，程序重启后可据此继续调度。

**为什么需要它**：内存随进程退出消失，但执行进度有时要保留。函数、网络连接等不能像普通数字和文字一样直接保存；密钥虽然能变成文字，也绝不能顺手放进检查点。

**在本项目里的角色**：eve 保存可丢弃的执行记录；动态 `step.started` 在真正执行模型时才从内存创建带密钥的模型，它不成为落盘的会话配置。应用自己的聊天、记忆和任务状态仍以 SQLite 为准。

**相关概念**：[[框架（framework）]]、[[管道（stdin/stdout）]]、[[回调（callback）]]

### 本地模拟与测试替身（mock）

**是什么**：用一个按测试要求固定回应的小程序，代替真实外部服务。比如本机开一个 HTTP 服务，总是返回“收到”和固定用量，不向智谱发请求。

**为什么需要它**：认证、密钥交付、失败处理和退出行为应该每次都能稳定复查，不能靠模型这次碰巧怎么回复；也避免自动检查花钱。

**在本项目里的角色**：Vitest 注入假调用函数检查业务分支；贯通脚本启动真实业务后台和 eve，只把供应商替换为本机假接口。T03 计划让工具替身对虚构资料返回固定成功或失败，观察模型是否如实回应；这种模拟不能证明真实记忆已经保存或删除。真实调用另测连通性，角色质量还需人工评价。

**相关概念**：[[HTTP 请求头（request header）]]、[[流（stream）]]、[[框架（framework）]]

### 子进程回收与进程编号（PID）

**是什么**：PID 是操作系统给运行程序分配的编号，用来查询或结束指定进程。父程序退出后，子程序若继续运行，就成了没人管理的残留进程。

**为什么需要它**：只关窗口不等于所有后台都退出；残留可能继续占端口、内存或发模型请求。需要明确谁负责关闭谁，还要考虑 Windows 强制结束程序时清理函数来不及执行。

**在本项目里的角色**：Electron 关业务后台，后台关 eve；eve 额外检查启动它的父 PID 是否仍存在。自动检查只查询本次创建的进程，避免按 node.exe 名字误杀其他软件。

**相关概念**：[[进程与 spawn]]、[[管道（stdin/stdout）]]

### 遥测与调用追踪（telemetry / tracing）

**是什么**：遥测是软件向维护方发送使用情况；调用追踪是把一次操作经过的步骤、输入或结果记录下来，用于排错。它们和实现功能所需的业务数据用途不同。

**为什么需要它**：定位慢在哪一步很有帮助，但记录内容可能包含提示词或回复。关闭日志显示也不代表追踪文件或外部上报一定关闭，需要分别设置。

**在本项目里的角色**：eve 构建关闭 CLI 遥测，作者目录关闭默认本地追踪，生产子进程的原始输出不落日志。应用只记录操作标识、错误码、耗时和用量；框架执行进度与 SQLite 业务数据仍按各自职责管理。

**相关概念**：[[序列化与工作流检查点（serialization / checkpoint）]]、[[环境变量（environment variable）]]

### Electron 的 Node 运行模式（ELECTRON_RUN_AS_NODE）

**是什么**：Electron 程序通常负责开窗口；用 `ELECTRON_RUN_AS_NODE=1` 启动时，同一个 exe 可以改为执行 Node 脚本。这是运行方式的公开开关，不是密钥。

**为什么需要它**：用户机器可能没有单独安装 Node。复用应用自带的运行环境，可以启动后台脚本；代价是后台可用的 Node 版本会跟随 Electron，升级时必须一起检查。

**在本项目里的角色**：desktop 层在打包后用应用自己的 exe 启动业务后台，后台再用同一个运行程序启动 eve。免安装目录已有进程启动和请求送达记录；安装后的数据库及无开发环境验收仍需单独完成。

**相关概念**：[[进程与 spawn]]、[[环境变量（environment variable）]]、[[原生驱动、ABI 与 Node-API]]

### 透明窗口与无边框窗口（transparent / frameless）

**是什么**：窗口是操作系统在桌面上划出的一块矩形区域。无边框窗口（frame: false）去掉标题栏和边框；透明窗口（transparent: true）允许矩形里没画内容的像素完全不显示，看起来只剩画的内容「浮」在桌面上。两者常一起用，是桌宠类软件的显示基础。

**为什么需要它**：角色是 Q 版立绘，不是矩形软件界面。窗口不透明的话，角色周围会拖着一个底色方块，把底下的桌面图标全挡住。透明窗口把「看见的角色」和「占用的桌面区域」分开，也为后续「透明区域不挡鼠标」的命中检查（T02）创造前提。

**在本项目里的角色**：T02 的透明角色小样——无边框透明窗显示一张带透明背景的占位 SVG，并关闭系统投影（hasShadow），避免透明的四角投出矩形阴影。Electron 透明窗在 Windows 上有平台限制（如系统截屏可能拍到黑块、个别显卡驱动不兼容），实际表现按 03 §3 的要求以真机验收为准。

**相关概念**：[[框架]]、[[编译与构建产物]]

### 远程调试端口（--remote-debugging-port / CDP）

**是什么**：Chromium/Electron 自带的「检修口」：启动时加参数 `--remote-debugging-port=端口号`，程序就在本机开一个 HTTP + WebSocket 服务，说一套叫 CDP（Chrome DevTools 协议）的话——能列出打开的页面、在页面里执行 JS、读页面内容。开发者按 F12 看到的 DevTools 就是靠这套协议通信的。

**为什么需要它**：打包后的应用没有开发工具入口，验收脚本也没法从外部「把手伸进」页面。要证明窗口里真的渲染出了内容（不是白屏）、并驱动它关窗，只能借这个官方检修口。

**在本项目里的角色**：`.eve/probe-packaged.mjs` 用它等窗口页面出现、核对标题、执行 `window.close()`；仅验收脚本用，正常运行不带此参数——检修口常开等于留一个能操纵页面的洞。

**相关概念**：[[回环地址与端口（127.0.0.1 / port）]]、[[Electron 的 Node 运行模式（ELECTRON_RUN_AS_NODE）]]、[[进程与 spawn]]

### 原生驱动、ABI 与 Node-API

**是什么**：原生驱动是用 C/C++ 等语言编译好的模块，JavaScript 可以调用它；ABI 是它与运行程序相互调用时必须匹配的约定。Node-API（也称 N-API）提供较稳定的接口，减少驱动对某个 Node 版本的依赖。

**为什么需要它**：驱动不只是几份 JavaScript 文件，还要匹配操作系统、处理器架构和运行时能力。看到文件存在、或某次加载成功，都不能推断其他运行环境也能用。

**在本项目里的角色**：data 层通过 better-sqlite3 调用 SQLite。本地已安装的 13.0.3 源码使用 Node-API；打包时暂不重建原生模块（`npmRebuild: false`），仍需用实际随包驱动验证文件读写、关闭进程后重开和无开发环境运行。

**相关概念**：[[编译与构建产物（build）]]、[[Electron 的 Node 运行模式（ELECTRON_RUN_AS_NODE）]]、[[迁移（migration）]]

### asar 档案与解包目录（asarUnpack）

**是什么**：asar 是 Electron 把许多应用文件收进一个档案的格式；`asarUnpack` 指定哪些文件要另放在旁边的普通目录中，通常叫 `app.asar.unpacked`。

**为什么需要它**：Electron 能识别档案内部路径，普通文件操作和独立后台程序不一定能。需要直接启动或加载的文件放到档案外，后台才能按真实磁盘路径找到它们。

**在本项目里的角色**：构建与 desktop 层协同：打包配置把后台入口、eve 产物和运行依赖放到解包目录，主进程再从该目录启动后台。文件已被打包不代表运行已通过，仍要实际启动和检查结果。

**相关概念**：[[编译与构建产物（build）]]、[[进程与 spawn]]、[[原生驱动、ABI 与 Node-API]]

### Git 忽略列表（.gitignore）

**是什么**：Git 是记录源码版本的工具；`.gitignore` 列出默认不把哪些未跟踪文件加入版本记录。它不会删除文件，也不会自动取消已经被 Git 跟踪的文件。

**为什么需要它**：依赖、安装程序和缓存通常能重新生成，不应混进源码提交；密钥也必须排除。忽略规则是一道提醒，提交前仍要检查实际准备提交的内容。

**在本项目里的角色**：仓库忽略依赖、构建产物、临时验证目录、密钥文件，以及本机测试时安装到仓库内的程序目录。加忽略规则保留本地文件，不影响已安装程序运行。

**相关概念**：[[编译与构建产物（build）]]、[[sha256 指纹]]

## 六、模型与角色

### 角色卡与提示词（character card / prompt）

**是什么**：提示词是每次调用模型时交给它的说明和内容；角色卡是其中描述人物性格、表达习惯、关系和背景的部分。原创对话示例展示可能的说法，帮助模型理解变化，不是要求它背诵的标准答案。

**为什么需要它**：只说「像六花」容易让回复只剩几个口头禅。把她在乎什么、怎样亲近、什么情况下认真起来写清楚，才有具体内容可试聊、比较和修改。文字写得完整，也仍需人工判断实际回复是否像角色。

**在本项目里的角色**：`app/characters/` 保存角色内容样稿；共同事实规则与六花核心设定分开，另有少量原创示例。它们目前没有接入模型调用，不会覆盖 T01 自测身份。后续由应用组织这些内容并管理人设版本，用户聊天与记忆仍以 SQLite 为准。

**相关概念**：[[模型上下文（context）]]、[[作者目录（authored directory）]]、[[事务（transaction）]]

### 模型上下文（context）

**是什么**：模型生成这一条回复时，实际能读到的全部输入。它不等于应用硬盘里的全部聊天记录；历史存在本地，不代表这一轮已交给模型。

**为什么需要它**：模型每次可读的内容有上限，输入也影响费用和等待时间。必须挑出本轮需要的资料；没带入的旧事不能靠模型猜出来补齐。

**在本项目里的角色**：服务层将共同规则、核心人设、少量相关示例、共享资料、相关记忆、最近对话和当前消息按规格组合。空间不足时优先保留核心人设和当前消息，减少旧对话与示例。角色卡样稿完成，只代表有了待组合的文字，不代表输入预算与记忆隔离已经实现。

**相关概念**：[[角色卡与提示词（character card / prompt）]]、[[本地模拟与测试替身（mock）]]

### 固定案例与人工盲评（evaluation case / blind evaluation）

**是什么**：固定案例是提前写好、比较时保持一致的测试话题和条件；人工盲评是暂时隐藏模型名称，让人先看实际回复再评分。

**为什么需要它**：不同模型遇到不同难度的话题，很难公平比较；提前知道品牌或价格也可能影响判断。用同一组多轮对话，才能看到改设定或换模型后具体哪里变好、哪里退步。

**在本项目里的角色**：T03 准备 24 组固定情境，第一阶段先运行指定的 12 组，由用户或熟悉角色的人评价。题目与评分标准保存在评测侧，模型只看到当前该回答的内容。记忆事实、工具结果和结束意愿单独判定，不能被高角色分抵消；目前只有空白材料，尚无实测成绩。

**相关概念**：[[角色卡与提示词（character card / prompt）]]、[[模型上下文（context）]]、[[本地模拟与测试替身（mock）]]
